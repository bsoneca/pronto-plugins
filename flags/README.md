# flags

Feature flags for a pronto app, on [OpenFeature](https://openfeature.dev) and [flagd](https://flagd.dev).

## What it adds

- The app says its flags in CUE (`flags_spec.cue`); generate turns them into flagd's definitions in `flags/flags.json`.
- flagd runs beside the door, as a container or a Cloud Run sidecar, and answers OpenFeature's remote protocol (OFREP) at `/ofrep/` on the app's own origin.
- Live flags: where the app is released, flagd reads one object in a versioned Cloud Storage bucket. `pronto-flags push --flip <flag>` (or `--flip <flag>=<value>`) changes a flag with no deploy (a push is a merge over the live flags), and `rollback` restores an earlier version.
- Files in the app: `flags_plugin.cue`, `pronto/flags.cue`, `flags/flags.nu`, and `flags_spec.cue` (written once, then the app's).
- The flags in the app's database: generate also writes `flags/flags.sql`, which an app with a database lists among its raw migrations. It adds `pronto_flags.flag_on(flag, player)`, which answers as flagd does (default, local at hand, accounts), so the database can refuse a feature's writes while its flag is off; a targeting that yields null or a variant the flag lacks reads the default variant (flagd's documented behaviour), but one the evaluator cannot evaluate (an operator it lacks, a malformed rule, a database error) raises, never the default. `pronto_flags.flag_on_strict(flag, player)` is the same read under the access gate's name (pronto-api's `api_on`, an app's key gate). A flag the database holds no document for is off. With `flagsLive.database` (the app's command that runs SQL on its stdin in the released database), every write of the live flags (push, its restore, rollback) is written there too, through `pronto_flags.put()`, with flagsLive.url's host; a write that fails there fails the push. A test database holds the flags baked into the image instead: one whose fixture inserts `pronto_flags.at_hand` and calls `pronto_flags.fill_local()` (a release's database never has the marker). To adopt it: reinstall, run `generate` twice (the first writes the rule that writes `flags/flags.sql` before pronto's writer, the second writes the file), then list it among the raw migrations, numbered before any migration that reads it.

```cue
flags: premium: {default: false, local: true}
```

## Use

From a pronto app:

```sh
<this repo>/bin/pronto-flags <app-dir>
# say the flags in flags_spec.cue
./saytw generate && ./saytw lint
```

Live flags, run as the operator's own gcloud login:

```sh
<this repo>/bin/pronto-flags setup|push|released|history|rollback|show|cases <app-dir>
```

A repo that pins pronto-flags (a commit in its `.github/flags.pin`, 40 hex characters) runs it through the repo's pinned entry point (in pronto: `tools/flags/pronto-flags`), never from a checkout of its own. Every write (`setup`, `push`, `released`, `rollback`, and the armies' `push` and `rollback`) first checks that this checkout contains the pinned commit, and refuses, before reading or writing anything, one that does not: a checkout older than the pin can turn off flags the release still reads (PRONTO-680, PRONTO-718). `show`, `history` and `cases` are not checked. Each version and journal line records the commit of the pronto-flags that wrote it (`plugin`).

A `push` is a merge over the live flags, never the spec written whole (PRONTO-680: a flag retired from main vanished from production while the release serving it still read it, and a default changed on main landed unasked):

- **`--flip a,b`** names the flips the push means, and sets the flag from the command line, not from the spec: `--flip X` turns X on, `--flip X=<value>` sets a bool (`true`/`false`), a string or a number (int and float are one kind; the value may hold commas, so one `name=value` is the whole `--flip`: mixing it with other names is refused, repeat the command), checked against the kind of the spec's default. The spec still supplies the flag's shape (its `local` value, hosts and accounts); the written entry is the spec's with its default set, and its cases run as before (`--flip X=false` runs none). A bare name on a non-bool is refused, and so is a bare name where the spec's default is false and live's is true (say `X=true` or `X=false`); a name the spec lacks is refused, with nothing written. A flag in both whose reach differs (default, accounts or targeting: `reach` in live.nu) keeps its live entry whole unless `--flip` or `--sync` names it, and the push says so on stderr; a bare push turns nothing on and changes no flag's accounts live. A flag new to the live object that is not fully off (default false, no accounts and no other targeting) is written off (default false, its accounts and canary gone, the at-hand branch kept) unless `--flip` or `--sync` names it, with a warning, and recorded under `kept` in the version's metadata and the journal; a new flag that is not a bool has no off form, so it is refused unless named. `setup`'s first push goes through the same merge.
- **`--sync a,b`** is what `--flip` meant before it took a value (PRONTO-1191): the flag's whole reach as the spec says it (default, accounts, targeting) is written to live. The cases, the rollback and the journal are the same; nothing is recorded back, since the spec already says it.
- **A flip is recorded back (`record`).** After the final successful write of a push that names `--flip`, or of a `rollback` (not after the automatic restore of a failed flip, nor under a dry run), the tool opens a pull request that writes into the app's `flags_spec.cue` the values of the version it wrote, for the flags it owns only: the `--flip` and `--sync` names (for a rollback, the flags whose default moved). The branch also keeps the flags the open record pull request (its `Records:` line) already changes against main, for as long as live still holds their value, so a second flip does not unmake the first's record; one whose live value moved on is dropped from it. A flag the spec holds differently that the push did not write (a held or written-off edit) is never recorded: `drift` shows it. A value is recorded only while live still holds it; if live has moved on, that is said on stderr, noted in the journal, and the flag is skipped (`record: skipped`). It works in a scratch worktree from a fresh `origin/main`, changing only the literal of each flag's depth-1 `default:`; accepted only if `cue export -e flagd.document` moves nowhere else and `cue vet` passes, then the app's generate (`deno run -A tests/slot.ts --weight 1 -- ./saytw generate`, stopped after `PRONTO_FLAGS_GENERATE_TIMEOUT_SEC`, 600) and a check that nothing outside the app's own files (never `.github/`) changed. The branch is `fix/flags-record-<app>`, rebuilt from main each time, with `gh pr merge --auto --squash`; an open one (this repository's, by the current gh user: a fork's is ignored) is edited (force with lease, retried once after a lost lease; a create that finds it already there edits it). The branch head and the open pull request (with its `Records:` line) are read together at the start of an attempt, and that head is the force-with-lease value, so a record that landed meanwhile fails the push and the attempt is made again over the fresh pull request; an unreadable `Records:` line carries nothing, with a warning; a pull request no longer open when the branch is pushed is replaced by a new one; an edit arms auto-merge again. When there is nothing to record, an open record pull request that names one of the flags is closed with its branch; a failed record is transient and leaves it open. A `record: pending` line is written to the journal (`event` `flags.record`) first, then the outcome (`pr`, `none`, `skipped`, `failed`). A record that cannot be made warns and never fails the push; a failed or closed record pull request never reverts live. `PRONTO_FLAGS_RECORD=off` skips it; `PRONTO_FLAGS_RECORD_BIN` stands in for it in tests (run as `<bin> <flag> <value as JSON> <version>` once per flag); `PRONTO_FLAGS_GENERATE_CMD` stands in for the generate command. `pronto-flags record <app> [--version V --flags a,b]` does it by hand.
- **`pronto-flags drift <app-dir>`** compares the reach of every flag the spec and live both hold, lists the differences and any open record pull request, and exits 1 when there are any (0 when equal). Read-only.
- **A live flag the spec no longer names** stays while the release being served reads it, and goes once the record says it does not (or with **`--drop a,b`**, which removes it whatever the record says, noted as forced; a flag the spec holds cannot be dropped).
- **The record** is `released.json` beside the live object (`gs://<bucket>/released.json`, or `<dir>/released.json`): `{commit, at, flags: [names]}`, the keys of the released tree's `flags/flags.json`, the file the flagd image bakes. **`released <app-dir>`** writes it from a clean released tree (CUE edits are refused, and a dry run refuses the write); release-cron runs it once production serves a release and when a run finds main already serving (`releaseCron.flagsReleased`), where a failure warns and never fails the run. With no record every live flag counts as read: kept, with a warning, exit 0.
- What a push kept and dropped is on the version's metadata (`kept`, `dropped`) and in the journal line. `show` prints the merged result. `rollback` still writes an old version whole.

A `push` that changes a flag's default value or accounts (a flag `--flip` or `--sync` names) or adds a flag that is on is a flip, and a flip writes the merged flags for everyone in one version, then runs the flag's `production` cases that need no tester on production, and a failure writes the version before it again. See [A flip runs its cases](../README.md#a-flip-runs-its-cases). In the spec: `flagsLive: {url}` (`testers`, `runAs` and `alert` are no longer read, PRONTO-284) and `flagsCases: {live}`; in the app's scenarios and unit cases, `flags: ["<flag>"]` (and `production: true` on the scenarios safe to run on production).

Every write (`setup`, `push`, `released`, `rollback`) prints `flags: target <url>` first, and refuses, with nothing written, a target other than `--expect <url>` (or `PRONTO_FLAGS_EXPECT`). With `--dry-run` (or `PRONTO_FLAGS_DRY_RUN=1`) a write shows what it would write and stops, and a dry run never writes, whatever path it takes: each place that writes refuses under it (every gcloud call but a read, the ssh mirror, the store itself) with `flags: dry run: refused a write`. A stand-in for gcloud is no dry run: on 2026-11-07 a test that faked gcloud through `SAYT_MISE_BIN`, run under `./saytw` (which sets its own), wrote the live bucket. Each write is also appended, as one JSON line, to the flip journal (`$XDG_STATE_HOME/pronto-flags/<app>.jsonl`, `~/.local/state` by default; `PRONTO_FLAGS_JOURNAL` names another file) and printed after `flags: journal `: `at`, `event` (`flags.write`), `app`, `target`, `version`, `from` (the generation it replaced), `stage`, `flag` (the flags whose default value moved, joined by `+`), `who`, `commit`, `cases`, `note` and `changes` (`[{flag, from, to}]`). `history --json` prints the versions as JSON, each with its `changes` against the version before it.

The store can be a local directory instead of a bucket, for a drill or a laptop: `flagsLive: {dir: "flagstore"}` (relative to the app's folder, or absolute). It keeps the bucket's semantics as files: the live document at `<dir>/flags.json` (written whole by a rename, so a flagd watching it never reads half), each version at `<dir>/versions/<generation>.json` with its `<generation>.meta.json`, a write refused when the generation it read is no longer the live one. It needs no gcloud, and a flagd reads it as a file source (`flagsLive.sources`).

Live flags need `flagsLive: {project, bucket}` in the spec and a flagd sidecar in `release.cue`. The page reads flags with OpenFeature's web SDK and the OFREP provider. Details in the [root README](../README.md#pronto-flags); why a flip runs its flag's cases, in [docs/flag-flips.md](../docs/flag-flips.md). There is no skill for this plugin.

## pronto-armies

The same push, one object kind over: an app whose page reads its armies from a database shape publishes them with `bin/pronto-armies push|show|history|rollback <app-dir>` (everyone at once, then the flag's `production` scenarios that need no tester, written back on a failure). See [pronto-armies](../README.md#pronto-armies-the-second-object-kind-of-the-push).

## Tests

- [`test/armies_test.nu`](test/armies_test.nu): the armies kind, against a stand-in for the app's SQL command ([`fake_sql.py`](test/fake_sql.py)): a local push, a live push for everyone and its cases (a signed-in scenario listed, not run), a push with no `production` scenario, a refusal with no cases, a failing case written back, the dry run, `--expect`, `history` and `rollback`.

- [`sql_test.ts`](sql_test.ts): `flags/flags.sql` on PGlite: `flag_on` with no document, a flag's default and accounts released, a test database's baked flags at hand, a push's document, a targeting it cannot evaluate (raised), null or an unknown variant (the default), a disabled flag, a quote in a value, and no write for an app role.
- [`install_test.ts`](install_test.ts): the installer: flags in the app's own package, its spec kept, a program with no package refused.
- [`live_test.ts`](live_test.ts) and [`test/live_test.nu`](test/live_test.nu): the live commands against a stand-in for gcloud ([`fake_gcloud.py`](test/fake_gcloud.py)) and for flagd's OFREP answer ([`fake_ofrep.py`](test/fake_ofrep.py)), with the app's cases as tiny `sh` commands: a flip refused with no cases or with no `flagsLive.url` (nothing written), `--untested` with its reason kept, a flag with no `production` scenario written for everyone with no case run, `--no-canary` accepted, the happy path (everyone, its cases, then passed, nothing at hand), a live failure and an OFREP timeout (rolled back). The merge (`keep-live`): a retired flag kept with no record, kept while the record names it and dropped once it does not, `--drop`, a changed default or changed accounts kept unless `--sync` or `--flip` names it (and a new flag on written off), accounts reordered no change, a flip that only adds accounts needing cases or `--untested` and telling the board nothing, an unknown `--flip` refused, `released` (the record, a dirty tree, a dry run) on a bucket and a directory, the database holding the merged document, and a failed flip's restore keeping the kept flags. A flip's record-back (a stand-in for the pull request, `PRONTO_FLAGS_RECORD_BIN`): `--flip X`, `--flip X=false`, a string value, a refused kind or bare name, a rollback and two flips recorded, never after a rolled-back flip or a dry run; the splice refusing a reference or a doubled default; and the real record against a git origin with a `gh` stand-in (branch, pull request, auto-merge, edit of the open one, a refused record noted in the journal) and `drift`. With `flagsLive.database` (a stand-in command that keeps the SQL), a push and a rollback put the document with flagsLive.url's host, a dry run writes nothing there, and a failure there fails the push. The same cases run on a directory store (flagsLive.dir), with the journal, `history --json`, `--expect`, the dry run and a stale write; with gcloud refusing every write (`FAKE_GCLOUD_READONLY`), `--dry-run` and `PRONTO_FLAGS_DRY_RUN` on push, rollback and setup write nothing, and the store and gcloud each refuse a write under a dry run on their own.

```sh
deno lint --no-config flags && FLAGD=$(mise where http:flagd)/flagd deno test --no-config --allow-read --allow-write --allow-run --allow-env --allow-net flags
./saytw --script tools.nu nu flags/test/live_test.nu
```
