# pronto-analytics

A plugin beside pronto, not part of it: the app holds the host's files, and its generate step
re-applies the door's routes. Business numbers are **not** journeys: they are `business_*`, have no
SLO and no alert, and travel by their own exporter. Journeys' alerts are held clear of them
(`#AnalyticsUnalerted`), and the schema refuses a name that could be a journey's or perf's.

## What the app gets

| Path | Owner |
| --- | --- |
| `pronto/analytics.cue` | regenerated: sql_exporter pinned, the `generate` rule (priority 3: after pronto's writer and the other hosts' door routes) |
| `analytics_plugin.cue` | regenerated: the schema (`#Analytics`), in the program's package |
| `analytics_hatch.cue` | regenerated: the `analytics` host-DOM hatch on every screen, the stand-in Umami and exporter targets, the door's host peer, the no-alert check |
| `shell/hatches/analytics/analytics.js` | regenerated: loads Umami's tracker through the terminal's script-URL policy, unless GPC or DNT |
| `shell/hatches/analytics/config.js` | regenerated by every generate: the Umami website id and tracker address |
| `analytics/analytics.nu`, `analytics/standin.ts` | regenerated: the generate step, the host exporter, the stand-in |
| `analytics/views.sql` | generated from the spec: list it in `code: state: rawMigrations` |
| `analytics_spec.cue` | seeded, then the app's: `analytics: #Analytics & {…}` |

## Adding it

```sh
${CLAUDE_PLUGIN_ROOT}/bin/pronto-analytics . [journeys=false]
```

then, in `analytics_spec.cue`, one entry in `metrics` per number:

```cue
business_orders: {
	help:   "Orders by state."
	labels: ["state"]
	select: "SELECT state, count(*) AS value FROM public.orders GROUP BY state"
}
business_signups_total: {type: "counter", help: "Accounts made.", labels: [], select: "SELECT count(*) AS value FROM public.users"}
```

Rules, each held by the schema or the vet:

- Names start `business_`; a counter ends `_total`, a gauge does not. A day's count is
  `increase(x_total[1d])` on the dashboard; a `_24h` gauge answers before history exists.
- `select` returns the labels named and a numeric `value`. A label holds few values: bucket anything a
  reader typed (top ten, "other"). No email, id or other personal data, ever.
- Read the app's tables with `public.` names; the views make a role that reads them and nothing
  else. A table another service creates when it starts (`needs: ["table"]`) leaves the metric empty
  until it is there.
- A panel's `expr` is PromQL over declared metrics with `app="$app"`.

List the screens that name their own hatches in `_analyticsOwnHatches` (the app's
`screen_hatches.cue`, as perf's and the journeys' are) and give each `analytics`.

Umami's website id comes from Umami, after the operator adds the site; write it in `analytics.umami.website`.

## Where it runs

pronto-infra's state holds the shared Grafana, Umami and the exporter's Cloud Run services
(`infra/gcp/analytics.cue`), and the Google accounts that may read Grafana. Adding a person is a line
in `grafanaUsers` there and `release@infra`.
